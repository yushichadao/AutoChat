# 逻辑与界面缺陷清单

> 这份文档记录**在代码里逐条核实过的缺陷**：现象、位置、影响、处理方式。
> 「已修」表示 2.0.0 里已经改掉并有回归测试；「待办」表示还需要人来做。

编号规则：`L` = 逻辑缺陷，`U` = 界面缺陷。

---

## 一、逻辑缺陷

### L1 手写 `WX_POLL_SQL` 被完全忽略（已修 · P0）

| 项 | 内容 |
| --- | --- |
| 位置 | `src/bridge/receiver.js` 的 `tick()` |
| 现象 | 配了 `WX_POLL_SQL` 的用户**一条消息都收不到**；日志里能看到在查库，但结果恒为空 |
| 根因 | 轮询改成「先取 local_id 批次 → 再按 id 逐条取行 → 再查 Name2Id」三段式后，`tick()` 里**无条件**改用 `buildPollSql(p.chatId)`；而手写 SQL 那条路径的 `p.chatId` 是空字符串，于是算出一个不存在的表名，用户写的 SQL 从来没被执行过 |
| 影响 | 所有选择手写 SQL 的用户完全收不到消息（README 明确支持这个用法） |
| 修法 | 区分两条取数路径：自动计划走三段式；手写 SQL 走「一条 SQL 直接返回完整行」，按约定别名解析 |
| 回归 | `test/receiver.test.js` 新增「按会话轮询：三段式」与「手写 SQL 路径」两组用例 |

### L2 接收路径重写后测试没跟上（已修 · P0）

| 项 | 内容 |
| --- | --- |
| 位置 | `test/receiver.test.js` |
| 现象 | `npm test` 在 2.0.0 开工前就是**红的**（2 条失败），而 README 声称「108 项全绿」；红灯被长期忽略 |
| 根因 | 轮询实现改成三段式后，测试里的假 hook 还在用旧的一步查询返回结构，取不到任何消息 |
| 影响 | 回归网失效：接收路径的大改动没有测试保护 |
| 修法 | 假 hook 改成「按 SQL 形态返回不同结果」，补上手写 SQL 路径与三段式路径的覆盖 |
| 回归 | 现为 231 项全绿 |

### L3 两份 `config.json` 读写实现（已修 · P1）

| 项 | 内容 |
| --- | --- |
| 位置 | 原 `src/cli/index.js` 与原 `src/setup/server.js` 各有一份 `readChats` / `writeChats` |
| 现象 | 两边写文件的格式与容错不同；CLI 侧非原子写，中途崩溃会留下半个 JSON |
| 修法 | 统一到 `src/core/chats.js`，写文件改成「临时文件 + rename」 |

### L4 两套环境体检（已修 · P1）

| 项 | 内容 |
| --- | --- |
| 位置 | `tools/check-env.js` 与 `src/tasks/doctor.js` |
| 现象 | 两个入口结论可能不一致（一个说「hook DLL 未配置」，另一个说「路径不存在」） |
| 修法 | `tools/check-env.js` 变成薄封装，转调 doctor，输出一致 |

### L5 两套卸载实现，能力不对等（已修 · P1）

| 项 | 内容 |
| --- | --- |
| 位置 | `tools/uninstall.js` 与 `src/tasks/install.js` |
| 现象 | 命令行卸载**没有**解除微信更新通道阻断，卸载后微信仍锁在旧版本（详见 [故障模式 F11](failure-modes.md)） |
| 修法 | 合并为一份实现：哈希比对还原 version.dll、`--force` 删除我们部署的 DLL、解除 update 阻断 |

### L6 `AI_ENABLED` 与 `AI_MASTER_SWITCH` 语义重复（已修 · P1）

| 项 | 内容 |
| --- | --- |
| 位置 | `src/core/config.js` |
| 现象 | 两个配置项都表示「要不要自动回复」，用户不知道该改哪个；界面里还各画了一个勾选框 |
| 修法 | 语义并入 `AI_ENABLED`；旧键仍被读取（旧键为 0 时同样视为不自动回复），体检提示「已废弃，请改用 `AI_ENABLED`」 |

### L7 界面出现两个语义重复的开关（已修 · P1）

| 项 | 内容 |
| --- | --- |
| 位置 | 原 `src/setup/ui/app.js` 的「启用 AI 回复」与「硬总开关」两个勾选框 |
| 现象 | 两个勾选框文案相近、用户分不清差别；同一个状态还要在顶栏徽标和状态卡里各说一遍 |
| 修法 | 全局只留**一个**「自动回复开关」（放状态卡），徽标改为「服务 / 自动回复 / 模型」，危险动作用按钮 + 二次确认代替开关 |

### L8 裸勾选框直接暴露给用户（已修 · P1）

| 项 | 内容 |
| --- | --- |
| 位置 | 原 `src/setup/ui/app.js` 的会话表 `input type=checkbox` |
| 现象 | 浏览器默认勾选框，没有说明、没有生效时机、和上面两个开关长得一样，误点风险高 |
| 修法 | 引入控件库 `switchRow / segRow / actRow / chipMulti`；**全仓禁止裸勾选框**，并用 `test/gui-widgets.test.js` 扫描强制 |

### L9 外部文本直接拼进 `innerHTML`（已修 · P1）

| 项 | 内容 |
| --- | --- |
| 位置 | 原会话表渲染：直接插入群名或昵称 |
| 现象 | 群名 / 昵称来自微信，**内容可控**；一个叫 `<img src=x onerror=...>` 的群就能在配置器里执行脚本 |
| 修法 | 所有外部文本统一走 `esc()` 转义后再插入 DOM；新增 `test/gui-cards.test.js` 断言群名被转义 |

### L10 静态资源路径穿越校验过弱（已修 · P1）

| 项 | 内容 |
| --- | --- |
| 位置 | 原 `src/setup/server.js` 的 `full.startsWith(UI_DIR)` |
| 现象 | 前缀判断对 `..` 归一化后的边界不严，存在读到 ui 目录外文件的风险 |
| 修法 | 改为 `path.resolve` 后按「等于根目录，或以根目录 + 分隔符开头」判断，并单独捕获非法 URL 编码 |

### L11 两套向导逻辑漂移（已修 · P1）

| 项 | 内容 |
| --- | --- |
| 位置 | 原 `src/cli/tui.js` 与原 `src/cli/index.js` 的 `cmdSetup` |
| 现象 | 两套向导各写各的：TUI 多了体检 / 锁版本 / 选 DLL / 注入模式，普通 setup 没有；两边说法也不一致 |
| 修法 | 合并到 `src/tasks/setup.js` 的步骤状态机，命令行与图形化配置器渲染同一份判断 |

### L12 源码结构混乱（已修 · P2）

| 项 | 内容 |
| --- | --- |
| 位置 | `src/config.js`、`src/logger.js`、`src/chats.js` 散在根目录；`src/setup/` 里混放安装、诊断、配置器服务端与前端 |
| 现象 | 想找「配置怎么读」得同时看 `src/config.js` 和 `src/cli/env-file.js`；配置器代码和 CLI 代码混在一个目录 |
| 修法 | 重排为 `core / tasks / cli / gui / ai / bridge / protocol` 六层，文件职责单一 |

### L13 输出无条件带 ANSI 转义（已修 · P2）

| 项 | 内容 |
| --- | --- |
| 位置 | 原 `src/cli/index.js` 的颜色常量 |
| 现象 | 把输出重定向到文件时，日志里全是 `[32m` 之类的转义符 |
| 修法 | 颜色跟随 `process.stdout.isTTY`，`--no-color` 可强制关闭 |

### L14 没有退出码约定（已修 · P2）

| 项 | 内容 |
| --- | --- |
| 现象 | 体检发现阻断项时进程仍返回 0，脚本没法判断「能不能用」 |
| 修法 | 统一 0 正常 / 1 参数或运行错误 / 2 体检存在阻断项；多数命令支持 `--json` |

### L15 缺基本可观测手段（已修 · P2）

| 项 | 内容 |
| --- | --- |
| 现象 | 没有版本命令、看不到日志、没法脚本化读状态 |
| 修法 | 新增 `autochat version` / `autochat logs` / `--json`；日志尾部读取有行数与字节上限，且只读固定两个文件 |

### L16 限流静默丢弃缺少说明（部分已修 · P2）

| 项 | 内容 |
| --- | --- |
| 位置 | `src/ai/limiter.js` / `src/ai/replier.js` |
| 现象 | 冷却 / 每小时上限 / 并发上限三条规则叠加时，请求被丢但日志口径不清，用户看到的是「不理人」而不是「被限流了」 |
| 修法 | 丢弃原因（cooldown / quota / concurrent）已在 `replier.js` 以 `info` 级记录「触发限流(xxx)，本次不回复」，默认日志即可见；另在每分钟状态行汇总「跳过 N」 |
| 待办 | 状态快照里进一步暴露「因冷却被跳过 / 因配额被跳过 / 因并发被跳过」三个独立计数，便于一眼区分 |

## 三、未采纳的建议（以及为什么）

| 建议 | 不采纳的原因 |
| --- | --- |
| 把「机器服务 / 自动回复 / 模型服务 / 会话」四类对象各做一个独立开关面板 | 层级太深反而更难懂；改为「一个对象一行 + 明确对象名 + 生效时机」，把差异写在说明里 |
| 界面里直接编辑任意 .env 键 | 会让人改坏关键配置；保持白名单（`src/tasks/config.js` 的 `EDITABLE_ENV`），命令行同样受限 |
| 给每个配置项加一句「建议值」 | 噪音大；只在用户填错时给提示（`reviewConfig` 已有配置点评） |
| 把 hook DLL 的下载做进程序 | 涉及第三方二进制分发与许可问题；本项目只提供获取指引与来源清单 |
